# 1. Описание

## 1.1. Описание модели

Рассматривается математическая модель динамического сервисного сбора для системы онлайн-бронирования столов с предзаказом блюд.

Модель использует:

* текущую загрузку ресторана;
* срочность бронирования;
* востребованность дня недели;
* востребованность временного слота;
* погодный контекст;
* выходные и праздничные дни.

Модель строится как иерархия:

1. сначала вычисляются параметры;
2. затем из параметров формируются блоки;
3. затем блоки объединяются в итоговый индекс спроса;
4. итоговый индекс спроса преобразуется в базовый сервисный сбор;
5. базовый сервисный сбор преобразуется в итоговый сервисный сбор с учетом бизнес-логики предзаказа.

---

## 1.2. Для чего она нужна

Модель нужна для того, чтобы сервисный сбор:

* не был фиксированным для всех бронирований;
* зависел от текущей загрузки ресторана;
* зависел от спроса на выбранный слот;
* учитывал внешний контекст;
* стимулировал более крупный предзаказ;
* был математически обоснован и пригоден для автоматического обновления по данным.

---

## 1.3. Бизнес-логика модели

Если пользователь оформляет бронирование без предзаказа, сервисный сбор не взимается.

Если пользователь оформляет предзаказ, сервисный сбор считается моделью.

Если сумма предзаказа достигает порога бесплатного сервиса, итоговый сервисный сбор становится равным нулю.

# 2. Параметры

## 2.1. Параметр текущей загрузки ресторана ( ρ_r )

### Описание параметра

Параметр ( ρ_r ) показывает долю занятых столов в ресторане ( r ) на выбранный временной интервал.

### Формула вычисления без истории

где:

( N_booked,r ) — число уже занятых столов ресторана ( r ) в выбранный интервал;
( N_all,r ) — общее число столов ресторана ( r );
( ρ_r ) — коэффициент текущей загрузки ресторана ( r ).

```text
ρ_r = N_booked,r / N_all,r
```

### Формула вычисления с историей

Параметр ( ρ_r ) не зависит от истории и вычисляется так же, как и без истории.

где:

( N_booked,r ) — число уже занятых столов ресторана ( r ) в выбранный интервал;
( N_all,r ) — общее число столов ресторана ( r );
( ρ_r ) — коэффициент текущей загрузки ресторана ( r ).

```text
ρ_r = N_booked,r / N_all,r
```

### Почему используется именно так

Такое задание делает параметр нормированным и сопоставимым для ресторанов разного размера. Абсолютное число занятых столов не подходит, так как 8 занятых столов для ресторана на 10 столов и для ресторана на 40 столов означают разные уровни загрузки.

---

## 2.2. Параметр срочности бронирования ( u_r )

### Описание параметра

Параметр ( u_r ) показывает, насколько близко ко времени визита оформляется бронирование в ресторане ( r ).

### Формула вычисления без истории

где:

( Δt_r ) — время от момента оформления бронирования до начала визита в ресторане ( r );
( T ) — параметр масштаба срочности;
( u_r ) — коэффициент срочности бронирования в ресторане ( r ).

```text
u_r = exp(-(Δt_r / T))
```

### Формула вычисления с историей

Параметр ( u_r ) не зависит от истории и вычисляется так же, как и без истории.

где:

( Δt_r ) — время от момента оформления бронирования до начала визита в ресторане ( r );
( T ) — параметр масштаба срочности;
( u_r ) — коэффициент срочности бронирования в ресторане ( r ).

```text
u_r = exp(-(Δt_r / T))
```

### Почему используется именно так

Экспоненциальная функция дает естественное убывание срочности: разница между бронью за 5 дней и за 4 дня меньше, чем разница между бронью за 2 часа и за 20 минут.

---

## 2.3. Параметр востребованности дня недели ( d )

### Описание параметра

Параметр ( d ) показывает, насколько выбранный день недели исторически востребован по успешным бронированиям.

### Формула вычисления без истории

При отсутствии истории используется постоянное стартовое значение.

где:

( d_0 ) — стартовое значение параметра востребованности дня недели;
( d ) — параметр востребованности дня недели.

```text
d = d_0
```

### Дефолтное значение без истории

где:

( d_0 ) — дефолтное значение параметра востребованности дня недели при отсутствии исторических данных.

```text
d_0 = 0.5
```

### Формула вычисления с историей

При наличии истории параметр вычисляется по успешным бронированиям по всей системе.

где:

( B_day,sel ) — количество успешных бронирований в выбранный день недели по всей системе;
( \max_j B_day,j ) — максимум успешных бронирований среди всех дней недели по всей системе;
( d ) — параметр востребованности дня недели.

```text
d = B_day,sel / max_j(B_day,j)
```

### Почему используется именно так

Параметр ( d ) должен отражать не положение дня в календаре, а фактическую востребованность дня по успешным бронированиям. Поэтому здесь используется нормированная историческая частота, а не циклическое кодирование.

---

## 2.4. Параметр востребованности временного слота ( t )

### Описание параметра

Параметр ( t ) показывает, насколько выбранный временной слот исторически востребован по успешным бронированиям.

### Формула вычисления без истории

При отсутствии истории используется постоянное стартовое значение.

где:

( t_0 ) — стартовое значение параметра востребованности временного слота;
( t ) — параметр востребованности временного слота.

```text
t = t_0
```

### Дефолтное значение без истории

где:

( t_0 ) — дефолтное значение параметра востребованности временного слота при отсутствии исторических данных.

```text
t_0 = 0.5
```

### Формула вычисления с историей

При наличии истории параметр вычисляется по успешным бронированиям по всей системе.

где:

( B_time,sel ) — количество успешных бронирований в выбранный временной слот по всей системе;
( \max_m B_time,m ) — максимум успешных бронирований среди всех временных слотов по всей системе;
( t ) — параметр востребованности временного слота.

```text
t = B_time,sel / max_m(B_time,m)
```

### Почему используется именно так

Параметр ( t ) отражает фактический спрос на слот, а не просто номер часа. Это делает модель ближе к реальной системе бронирования.

---

## 2.5. Параметр востребованности стола ( p )

### Описание параметра

Параметр ( p ) показывает востребованность стола. В финальной глобальной модели для всех столов используется одинаковое значение.

### Формула вычисления без истории

где:

( p_0 ) — постоянное стартовое значение параметра востребованности стола;
( p ) — параметр востребованности стола.

```text
p = p_0
```

### Дефолтное значение без истории

где:

( p_0 ) — дефолтное значение параметра востребованности стола при отсутствии исторических данных.

```text
p_0 = 0.5
```

### Формула вычисления с историей

В данной версии модели параметр ( p ) не обновляется по истории и остается постоянным.

где:

( p_0 ) — постоянное стартовое значение параметра востребованности стола;
( p ) — параметр востребованности стола.

```text
p = p_0
```

### Почему используется именно так

Итоговая модель выбрана глобальной для всех ресторанов и без индивидуальной настройки столов. Это упрощает внедрение и исключает необходимость отдельного анализа популярности столов в каждом ресторане.

## 2.6. Параметр погодного контекста ( w_r )

### Описание параметра

Параметр ( w_r ) отражает влияние текущей погоды для ресторана ( r ) на уровень спроса.

Параметр ( w_r ) строится на основе аппарата нечеткой логики. Текущая погода не относится жестко только к одному классу, а может одновременно принадлежать нескольким классам спроса с разной степенью принадлежности. Для этого используются нечеткие множества погодных состояний и функции принадлежности:

* классу низкого спроса;
* классу среднего спроса;
* классу высокого спроса.

Итоговое значение ( w_r ) формируется как взвешенное среднее по степеням принадлежности текущей погоды к указанным классам.

### Формула вычисления без истории

При отсутствии истории используются экспертные коэффициенты погодных классов.

где:

( μ^w_1,r ) — степень принадлежности текущей погоды ресторана ( r ) к погодному классу низкого спроса;
( μ^w_2,r ) — степень принадлежности текущей погоды ресторана ( r ) к погодному классу среднего спроса;
( μ^w_3,r ) — степень принадлежности текущей погоды ресторана ( r ) к погодному классу высокого спроса;
( c^w_1 ) — экспертный коэффициент погодного класса низкого спроса;
( c^w_2 ) — экспертный коэффициент погодного класса среднего спроса;
( c^w_3 ) — экспертный коэффициент погодного класса высокого спроса;
( w_r ) — параметр погодного контекста ресторана ( r ).

```text
w_r = (μ^w_1,r·c^w_1 + μ^w_2,r·c^w_2 + μ^w_3,r·c^w_3) / (μ^w_1,r + μ^w_2,r + μ^w_3,r)
```

### Дефолтные значения без истории

где:

( c^w_1 ) — дефолтный коэффициент погодного класса низкого спроса при отсутствии исторических данных;
( c^w_2 ) — дефолтный коэффициент погодного класса среднего спроса при отсутствии исторических данных;
( c^w_3 ) — дефолтный коэффициент погодного класса высокого спроса при отсутствии исторических данных.

```text
c^w_1 = 0.3
```

```text
c^w_2 = 0.6
```

```text
c^w_3 = 1.0
```

### Формула вычисления с историей

При наличии истории коэффициенты погодных классов вычисляются по успешным бронированиям всей системы.

где:

( B_w,1 ) — количество успешных бронирований, пришедшихся на погодный класс низкого спроса по всей системе;
( B_w,2 ) — количество успешных бронирований, пришедшихся на погодный класс среднего спроса по всей системе;
( B_w,3 ) — количество успешных бронирований, пришедшихся на погодный класс высокого спроса по всей системе;
( c^w_1 ) — коэффициент погодного класса низкого спроса;
( c^w_2 ) — коэффициент погодного класса среднего спроса;
( c^w_3 ) — коэффициент погодного класса высокого спроса.

```text
c^w_1 = (B_w,1) / (max(B_w,1, B_w,2, B_w,3))
```

```text
c^w_2 = (B_w,2) / (max(B_w,1, B_w,2, B_w,3))
```

```text
c^w_3 = (B_w,3) / (max(B_w,1, B_w,2, B_w,3))
```

где:

( μ^w_1,r ) — степень принадлежности текущей погоды ресторана ( r ) к погодному классу низкого спроса;
( μ^w_2,r ) — степень принадлежности текущей погоды ресторана ( r ) к погодному классу среднего спроса;
( μ^w_3,r ) — степень принадлежности текущей погоды ресторана ( r ) к погодному классу высокого спроса;
( c^w_1 ) — коэффициент погодного класса низкого спроса;
( c^w_2 ) — коэффициент погодного класса среднего спроса;
( c^w_3 ) — коэффициент погодного класса высокого спроса;
( w_r ) — параметр погодного контекста ресторана ( r ).

```text
w_r = (μ^w_1,r·c^w_1 + μ^w_2,r·c^w_2 + μ^w_3,r·c^w_3) / (μ^w_1,r + μ^w_2,r + μ^w_3,r)
```

### Почему используется именно так

Погода плохо описывается жесткими порогами. Нечеткая логика позволяет учитывать промежуточные состояния, а исторические коэффициенты связывают эти состояния с реальным спросом.

## 2.7. Параметр выходных и праздничных дней ( h_r )

### Описание параметра

Параметр ( h_r ) отражает влияние календарного статуса дня для ресторана ( r ) на уровень спроса.

Параметр ( h_r ) также строится на основе аппарата нечеткой логики. Текущий день может не принадлежать строго только одному классу, а одновременно иметь признаки:

* рабочего дня;
* выходного дня;
* праздничного дня;
* пикового праздничного дня.

Для этого используются нечеткие множества календарных состояний и соответствующие функции принадлежности. Итоговое значение ( h_r ) определяется как взвешенное среднее по степеням принадлежности текущего дня к этим календарным классам.

### Формула вычисления без истории

При отсутствии истории используются экспертные коэффициенты календарных классов.

где:

( μ^h_1,r ) — степень принадлежности дня ресторана ( r ) к рабочему дню;
( μ^h_2,r ) — степень принадлежности дня ресторана ( r ) к выходному дню;
( μ^h_3,r ) — степень принадлежности дня ресторана ( r ) к праздничному дню;
( μ^h_4,r ) — степень принадлежности дня ресторана ( r ) к пиковому праздничному дню;
( c^h_1 ) — экспертный коэффициент рабочего дня;
( c^h_2 ) — экспертный коэффициент выходного дня;
( c^h_3 ) — экспертный коэффициент праздничного дня;
( c^h_4 ) — экспертный коэффициент пикового праздничного дня;
( h_r ) — параметр выходных и праздничных дней ресторана ( r ).

```text
h_r = (μ^h_1,r·c^h_1 + μ^h_2,r·c^h_2 + μ^h_3,r·c^h_3 + μ^h_4,r·c^h_4) / (μ^h_1,r + μ^h_2,r + μ^h_3,r + μ^h_4,r)
```

### Дефолтные значения без истории

где:

( c^h_1 ) — дефолтный коэффициент рабочего дня при отсутствии исторических данных;
( c^h_2 ) — дефолтный коэффициент выходного дня при отсутствии исторических данных;
( c^h_3 ) — дефолтный коэффициент праздничного дня при отсутствии исторических данных;
( c^h_4 ) — дефолтный коэффициент пикового праздничного дня при отсутствии исторических данных.

```text
c^h_1 = 0.4
```

```text
c^h_2 = 0.7
```

```text
c^h_3 = 0.9
```

```text
c^h_4 = 1.0
```

### Формула вычисления с историей

При наличии истории коэффициенты календарных классов вычисляются по успешным бронированиям всей системы.

где:

( B_h,1 ) — количество успешных бронирований, пришедшихся на рабочие дни по всей системе;
( B_h,2 ) — количество успешных бронирований, пришедшихся на выходные дни по всей системе;
( B_h,3 ) — количество успешных бронирований, пришедшихся на праздничные дни по всей системе;
( B_h,4 ) — количество успешных бронирований, пришедшихся на пиковые праздничные дни по всей системе;
( c^h_1 ) — коэффициент рабочего дня;
( c^h_2 ) — коэффициент выходного дня;
( c^h_3 ) — коэффициент праздничного дня;
( c^h_4 ) — коэффициент пикового праздничного дня.

```text
c^h_1 = (B_h,1) / (max(B_h,1, B_h,2, B_h,3, B_h,4))
```

```text
c^h_2 = (B_h,2) / (max(B_h,1, B_h,2, B_h,3, B_h,4))
```

```text
c^h_3 = (B_h,3) / (max(B_h,1, B_h,2, B_h,3, B_h,4))
```

```text
c^h_4 = (B_h,4) / (max(B_h,1, B_h,2, B_h,3, B_h,4))
```

где:

( μ^h_1,r ) — степень принадлежности дня ресторана ( r ) к рабочему дню;
( μ^h_2,r ) — степень принадлежности дня ресторана ( r ) к выходному дню;
( μ^h_3,r ) — степень принадлежности дня ресторана ( r ) к праздничному дню;
( μ^h_4,r ) — степень принадлежности дня ресторана ( r ) к пиковому праздничному дню;
( c^h_1 ) — коэффициент рабочего дня;
( c^h_2 ) — коэффициент выходного дня;
( c^h_3 ) — коэффициент праздничного дня;
( c^h_4 ) — коэффициент пикового праздничного дня;
( h_r ) — параметр выходных и праздничных дней ресторана ( r ).

```text
h_r = (μ^h_1,r·c^h_1 + μ^h_2,r·c^h_2 + μ^h_3,r·c^h_3 + μ^h_4,r·c^h_4) / (μ^h_1,r + μ^h_2,r + μ^h_3,r + μ^h_4,r)
```

### Почему используется именно так

Календарный контекст имеет промежуточные состояния. Например, обычный выходной и предпраздничный вечер — это разные по спросу ситуации. Нечеткая логика и исторические коэффициенты позволяют это учесть.

# 3. Блоки

## 3.1. Блок нагрузки (B_load,r)

### Описание блока

Блок (B_load,r) описывает текущую нагрузку на ресторан ( r ) и учитывает загрузку, срочность бронирования и их совместное влияние.

### Веса блока

Для блока используются веса:

* (W_l1)
* (W_l2)
* (W_l3)

### Как берутся веса без истории

При отсутствии истории используются экспертные глобальные значения.

где:

(W_l1) — вес влияния загрузки ресторана;

### Корреляционная функция ( corr(·,·) )

В формулах оценки важности факторов и блоков используется функция корреляции ( corr(x,y) ).

где:

( x ) — рассматриваемый параметр, фактор или блок модели;
( y ) — фактический показатель реализованного спроса;
( corr(x,y) ) — коэффициент корреляции между величинами ( x ) и ( y ).

Коэффициент корреляции показывает, насколько сильно изменение одной величины связано с изменением другой величины.

Если:

* ( corr(x,y) > 0 ), то при увеличении ( x ) величина ( y ) в среднем также увеличивается;
* ( corr(x,y) < 0 ), то при увеличении ( x ) величина ( y ) в среднем уменьшается;
* ( corr(x,y) ≈ 0 ), то линейная связь между величинами выражена слабо.

В данной модели используется абсолютное значение корреляции:

```text
|corr(x,y)|
```

где:

( |corr(x,y)| ) — абсолютная величина коэффициента корреляции между ( x ) и ( y ).

Использование модуля необходимо потому, что для оценки важности фактора значима не направленность связи, а ее сила. То есть как сильная прямая связь, так и сильная обратная связь свидетельствуют о том, что фактор существенно влияет на реализованный спрос.

# 5. Описание того, что все веса для всех ресторанов одинаковы, и что остается не одинаковым

В данной версии модели все веса являются глобальными и одинаковыми для всех ресторанов системы.

Одинаковыми для всех ресторанов являются:

* веса блоков ( W_{l1}, W_{l2}, W_{l3} );
* веса блока исторической востребованности ( W_{h1}, W_{h2}, W_{h3} );
* веса блока внешнего контекста ( W_{c1}, W_{c2} );
* веса итогового индекса спроса ( Z_1, Z_2, Z_3 );
* параметры тарификации ( S_{min}, S_{max}, k, z_0, D_{free}, γ ).

Не одинаковыми остаются:

* ( ρ_r ), потому что загрузка у каждого ресторана своя;
* ( u_r ), потому что время до визита у каждого бронирования свое;
* ( w_r ), потому что погода и принадлежность к погодным классам могут зависеть от конкретного ресторана и момента времени;
* ( h_r ), потому что календарный контекст относится к конкретной дате бронирования;
* ( z_r ), потому что итоговый индекс спроса считается для конкретного ресторана и конкретного бронирования;
* (S_base,r) и (S_final,r), потому что они вычисляются для конкретного ресторана и конкретного бронирования.

Параметры ( d ) и ( t ) в глобальной модели вычисляются по общей истории всей системы и потому не различаются между ресторанами для одного и того же выбранного дня недели и временного слота.

Параметр ( p ) в данной версии вообще фиксирован и одинаков для всех столов.

# 6. Плюсы и минусы модели

## Плюсы модели

1. **Простота внедрения.**
   Не требуется отдельная настройка весов для каждого ресторана.

2. **Устойчивость.**
   Глобальные веса обновляются по общей статистике всей системы, поэтому они менее шумные, чем ресторан-специфические веса.

3. **Отсутствие проблемы локального холодного старта.**
   Модель сразу работает для новых ресторанов, потому что не требует собственной длинной истории.

4. **Интерпретируемость.**
   Каждый параметр и каждый блок имеют понятный смысл.

5. **Возможность постепенного обновления.**
   При накоплении истории параметры ( d, t, w_r, h_r ) и веса ( W, Z ) могут уточняться без изменения структуры модели.

6. **Подходит для диплома.**
   Модель достаточно математически содержательная, но при этом не перегружена и легко объясняется.

## Минусы модели

1. **Нет индивидуальной настройки под конкретный ресторан.**
   Все рестораны используют одинаковые веса.

2. **Параметр стола упрощен.**
   Популярность конкретных столов не анализируется.

3. **Нет прямой оптимизации прибыли.**
   Модель строит сервисный сбор по индексу спроса, а не решает задачу максимизации ожидаемой выручки.

4. **Исторические индексы дня и времени глобальные.**
   Если у конкретного ресторана спрос сильно отличается от среднесистемного, модель это не учитывает.

# 7. Рассказ о модели с вероятностью и почему ее не взяли

Альтернативным вариантом была модель, в которой сервисный сбор выбирался через вероятность подтверждения бронирования.

Идея этой модели состояла в том, что:

1. сначала строится индекс спроса;
2. затем по сервисному сбору и индексу спроса оценивается вероятность, что пользователь завершит бронирование;
3. затем выбирается такой сервисный сбор, который максимизирует ожидаемую выгоду.

### Формула вероятности подтверждения бронирования

где:

( S ) — сервисный сбор;
( a ) — коэффициент чувствительности пользователя к цене;
( θ(z) ) — допустимый уровень сервисного сбора при индексе спроса ( z );
( P_acc(S | z) ) — вероятность того, что пользователь подтвердит бронирование.

```text
P_acc(S | z) = 1 / (1 + exp(a·(S - θ(z))))
```

### Формула ожидаемой выгоды

где:

( P_acc(S | z) ) — вероятность подтверждения бронирования;
( D ) — сумма предзаказа;
( S ) — сервисный сбор;
( J(S) ) — ожидаемая выгода.

```text
J(S) = P_acc(S | z)·(D+S)
```

### Почему эту модель не взяли

1. **Неясно, что считать отказом.**
   Пользователь мог не завершить бронирование по разным причинам: передумал, закрыл страницу, отвлекся, столкнулся с технической проблемой.

2. **Нет надежных данных о незавершенных действиях.**
   Для такой модели нужно отслеживать не только успешные бронирования, но и поведение пользователей на промежуточных шагах.

3. **Сложность интерпретации.**
   Даже если пользователь не завершил бронирование, невозможно однозначно доказать, что причиной был именно сервисный сбор.

4. **Высокая сложность реализации.**
   Требуется развитая система аналитики пользовательской воронки.

5. **Низкая практическая устойчивость для первой версии системы.**
   При отсутствии качественных данных об отказах параметры вероятностной модели становятся слишком условными.

### Почему выбрана именно текущая модель

Текущая модель опирается только на успешно оформленные бронирования, которые являются надежными и однозначно фиксируемыми событиями. Это делает модель:

* более устойчивой;
* проще реализуемой;
* легче объяснимой;
* более пригодной для первой версии платформы и для дипломного исследования.
