# Динамический сервисный сбор: математическая модель и план реализации

## 1. Назначение модели

Модель динамического сервисного сбора используется в системе онлайн-бронирования столов в ресторанах и кафе с возможностью предзаказа блюд. Ее задача — определить размер сервисного сбора для конкретного бронирования с учетом текущего и исторического спроса.

Сервисный сбор отражает не стоимость выбранных блюд, а востребованность самого бронирования: дату, время, выбранный стол, текущую загрузку ресторана и календарный контекст.

В модели не используется погодный параметр. Это упрощает реализацию, снижает зависимость от внешних источников данных и оставляет только те факторы, которые фиксируются внутри системы или однозначно определяются по календарю.

Модель должна обеспечивать:

- учет текущей загрузки ресторана;
- учет срочности оформления бронирования;
- учет исторической востребованности дня недели;
- учет исторической востребованности временного интервала;
- учет исторической востребованности выбранного стола;
- учет календарного статуса дня;
- работу при отсутствии истории за счет дефолтных значений;
- последующее уточнение весов на основе исторических данных;
- плавное изменение сервисного сбора внутри допустимого диапазона ресторана.

## 2. Основные бизнес-правила

Сервисный сбор применяется только при наличии предзаказа блюд.

Если пользователь создает бронирование без предзаказа, сервисный сбор равен нулю:

```math
P_r = 0, \quad A = 0
```

Если пользователь создает бронирование с предзаказом, сервисный сбор рассчитывается по модели спроса:

```math
P_r = P_r^{calc}, \quad A > 0
```

Итоговая стоимость бронирования с предзаказом определяется следующим образом:

```math
T = A + P_r
```

где:

- `T` — итоговая стоимость бронирования с предзаказом;
- `A` — стоимость выбранных пользователем блюд;
- `P_r` — применяемый сервисный сбор ресторана `r`;
- `P_r^{calc}` — расчетное значение сервисного сбора, полученное по модели спроса.

Сумма предзаказа не используется для увеличения или уменьшения сервисного сбора. Она используется только как признак применения сбора и как часть итоговой стоимости.

## 3. Общая схема модели

Модель имеет иерархическую структуру:

```text
параметры модели
      ↓
блок нагрузки, блок исторической востребованности, блок календарного контекста
      ↓
итоговый индекс спроса
      ↓
расчетное значение сервисного сбора
      ↓
применяемый сервисный сбор с учетом наличия предзаказа
```

Все параметры приводятся к единому направлению интерпретации: чем больше значение параметра, тем выше предполагаемый спрос. Значения параметров нормируются в диапазоне `[0; 1]`.

```math
0 \leq x \leq 1
```

где `x` — любой нормированный параметр модели.

## 4. Параметры модели

### 4.1. Параметр текущей загрузки ресторана

Параметр текущей загрузки показывает долю занятых столов ресторана на выбранный временной интервал.

```math
L_r = \frac{B_r}{M_r}
```

где:

- `L_r` — коэффициент текущей загрузки ресторана `r`;
- `B_r` — количество уже занятых столов ресторана `r` в выбранный интервал;
- `M_r` — общее количество столов ресторана `r`.

Если `M_r = 0`, расчет считается невозможным, так как ресторан без столов не может участвовать в бронировании.

### 4.2. Параметр срочности бронирования

Параметр срочности показывает, насколько близко ко времени визита оформляется бронирование. Чем меньше времени остается до начала визита, тем выше значение параметра.

```math
U_r = e^{-\frac{\Delta t}{\tau}}
```

где:

- `U_r` — коэффициент срочности бронирования в ресторане `r`;
- `\Delta t` — время от момента оформления бронирования до начала визита;
- `\tau` — параметр масштаба срочности.

Параметр `\tau` должен быть больше нуля. Если время визита уже прошло, бронирование считается некорректным и модель для него не применяется.

### 4.3. Параметр востребованности дня недели

Параметр показывает, насколько выбранный день недели исторически востребован по успешным бронированиям конкретного ресторана.

Если истории недостаточно, используется дефолтное значение:

```math
D_r(d) = D_0(d)
```

Если история накоплена, параметр рассчитывается по успешным бронированиям:

```math
D_r(d) = \frac{N_r(d)}{\max_d N_r(d)}
```

где:

- `D_r(d)` — востребованность дня недели `d` для ресторана `r`;
- `D_0(d)` — дефолтное значение востребованности дня недели;
- `N_r(d)` — количество успешных бронирований ресторана `r` в день недели `d`;
- `\max_d N_r(d)` — максимальное количество успешных бронирований среди всех дней недели ресторана `r`.

### 4.4. Параметр востребованности временного интервала

Параметр показывает, насколько выбранный временной интервал исторически востребован по успешным бронированиям ресторана.

Если истории недостаточно, используется дефолтное значение:

```math
V_r(t) = V_0(t)
```

Если история накоплена, параметр рассчитывается следующим образом:

```math
V_r(t) = \frac{N_r(t)}{\max_t N_r(t)}
```

где:

- `V_r(t)` — востребованность временного интервала `t` для ресторана `r`;
- `V_0(t)` — дефолтное значение востребованности временного интервала;
- `N_r(t)` — количество успешных бронирований ресторана `r` во временном интервале `t`;
- `\max_t N_r(t)` — максимальное количество успешных бронирований среди всех временных интервалов ресторана `r`.

Если пользователь выбирает произвольное время начала и окончания визита, выбранное время должно быть отнесено к одной или нескольким группам: завтрак, обед, вечерний пик, поздний вечер. Для длинного бронирования может применяться средневзвешенное значение по пересечению с несколькими интервалами.

### 4.5. Параметр востребованности стола

Параметр показывает историческую востребованность выбранного стола в ресторане.

Если истории по столам недостаточно, используется дефолтное значение:

```math
Q_r(q) = Q_0
```

Если история накоплена, параметр рассчитывается следующим образом:

```math
Q_r(q) = \frac{N_r(q)}{\max_q N_r(q)}
```

где:

- `Q_r(q)` — востребованность стола `q` в ресторане `r`;
- `Q_0` — дефолтное значение востребованности стола;
- `N_r(q)` — количество успешных бронирований выбранного стола `q`;
- `\max_q N_r(q)` — максимальное количество успешных бронирований среди всех столов ресторана `r`.

Если по столам нет достаточной статистики, параметр не должен усиливать вес модели на основе корреляции.

### 4.6. Параметр календарного контекста

Параметр календарного контекста отражает влияние статуса дня на уровень спроса. День может иметь признаки рабочего дня, выходного дня, праздничного дня или пикового праздничного дня.

```math
C_r = \frac{\mu_w c_{r,w} + \mu_e c_{r,e} + \mu_h c_{r,h} + \mu_p c_{r,p}}{\mu_w + \mu_e + \mu_h + \mu_p}
```

где:

- `C_r` — параметр календарного контекста ресторана `r`;
- `\mu_w` — степень принадлежности дня к рабочему дню;
- `\mu_e` — степень принадлежности дня к выходному дню;
- `\mu_h` — степень принадлежности дня к праздничному дню;
- `\mu_p` — степень принадлежности дня к пиковому праздничному дню;
- `c_{r,w}` — коэффициент рабочего дня для ресторана `r`;
- `c_{r,e}` — коэффициент выходного дня для ресторана `r`;
- `c_{r,h}` — коэффициент праздничного дня для ресторана `r`;
- `c_{r,p}` — коэффициент пикового праздничного дня для ресторана `r`.

Если сумма степеней принадлежности равна нулю, используется нейтральное дефолтное значение календарного контекста.

При наличии истории коэффициент календарного класса может определяться по относительной интенсивности спроса:

```math
I_{r,c} = \frac{\frac{N_{r,c}}{O_{r,c}}}{\max_c \frac{N_{r,c}}{O_{r,c}}}
```

где:

- `I_{r,c}` — относительная интенсивность спроса календарного класса `c` для ресторана `r`;
- `N_{r,c}` — количество успешных бронирований, пришедшихся на календарный класс `c`;
- `O_{r,c}` — количество наблюдений, относящихся к календарному классу `c`.

## 5. Блоки модели

### 5.1. Блок нагрузки

Блок нагрузки учитывает текущую загрузку ресторана, срочность бронирования и их совместное влияние.

```math
B_{L,r} = w_L L_r + w_U U_r + w_{LU} L_r U_r
```

где:

- `B_{L,r}` — значение блока нагрузки ресторана `r`;
- `w_L` — вес влияния текущей загрузки;
- `w_U` — вес влияния срочности;
- `w_{LU}` — вес совместного влияния загрузки и срочности.

Совместный компонент `L_r U_r` нужен для учета ситуации, когда высокая загрузка и высокая срочность одновременно усиливают уровень спроса.

### 5.2. Блок исторической востребованности

Блок исторической востребованности описывает спрос на выбранный день недели, временной интервал и стол.

```math
B_{H,r} = w_D D_r(d) + w_V V_r(t) + w_Q Q_r(q)
```

где:

- `B_{H,r}` — значение блока исторической востребованности ресторана `r`;
- `w_D` — вес востребованности дня недели;
- `w_V` — вес востребованности временного интервала;
- `w_Q` — вес востребованности выбранного стола.

### 5.3. Блок календарного контекста

Блок календарного контекста учитывает только календарный статус выбранного дня.

```math
B_{C,r} = C_r
```

где:

- `B_{C,r}` — значение блока календарного контекста ресторана `r`;
- `C_r` — параметр календарного контекста ресторана `r`.

Так как в блоке остается один параметр, отдельные внутренние веса для блока календарного контекста не используются.

## 6. Итоговая модель

### 6.1. Итоговый индекс спроса

Итоговый индекс спроса объединяет три блока: блок нагрузки, блок исторической востребованности и блок календарного контекста.

```math
Z_r = \alpha_L B_{L,r} + \alpha_H B_{H,r} + \alpha_C B_{C,r}
```

где:

- `Z_r` — итоговый индекс спроса ресторана `r`;
- `\alpha_L` — вес блока нагрузки;
- `\alpha_H` — вес блока исторической востребованности;
- `\alpha_C` — вес блока календарного контекста.

При отсутствии истории используются стартовые экспертные веса. При наличии истории веса могут обновляться по силе связи соответствующих блоков с фактическим реализованным спросом.

### 6.2. Преобразование индекса спроса в сервисный сбор

Расчетное значение сервисного сбора задается сигмоидальной функцией от итогового индекса спроса. Сигмоида переводит нормированный индекс спроса в денежное значение внутри допустимого диапазона ресторана.

```math
P_r^{calc} = P_r^{min} + \frac{P_r^{max} - P_r^{min}}{1 + e^{-k(Z_r - c)}}
```

где:

- `P_r^{calc}` — расчетное значение сервисного сбора ресторана `r`;
- `P_r^{min}` — нижняя граница сервисного сбора ресторана `r`;
- `P_r^{max}` — верхняя граница сервисного сбора ресторана `r`;
- `k` — коэффициент крутизны сигмоидальной функции;
- `c` — центр сигмоидальной функции.

Для предотвращения некорректных конфигураций проверяется условие:

```math
P_{sys}^{min} \leq P_r^{min} \leq P_r^{max} \leq P_{sys}^{max}
```

где:

- `P_{sys}^{min}` — системная минимально допустимая граница сервисного сбора;
- `P_{sys}^{max}` — системная максимально допустимая граница сервисного сбора.

### 6.3. Применяемый сервисный сбор

Применяемый сервисный сбор зависит от наличия предзаказа.

```math
P_r =
\begin{cases}
0, & A = 0, \\
P_r^{calc}, & A > 0.
\end{cases}
```

Итоговая стоимость:

```math
T = A + P_r
```

## 7. Обновление весов на основе истории

Исторические веса обновляются по наблюдениям конкретного ресторана. Одно наблюдение — это временной интервал ресторана за конкретную дату, для которого известны значения параметров модели, количество успешных бронирований и количество доступных столов.

Фактический реализованный спрос:

```math
y_{i,r} = \frac{N_{i,r}^{success}}{N_{i,r}^{available}}
```

где:

- `y_{i,r}` — фактический реализованный спрос в наблюдении `i` для ресторана `r`;
- `N_{i,r}^{success}` — количество успешных бронирований в наблюдении `i`;
- `N_{i,r}^{available}` — количество доступных столов или доступных мест в наблюдении `i`.

Успешным бронированием считается бронирование, которое было подтверждено рестораном и не было отменено до наступления времени визита.

Для оценки важности параметра или блока используется положительная часть коэффициента корреляции с фактическим спросом:

```math
s_x = \max(0, corr(x, y))
```

где:

- `s_x` — важность параметра или блока `x`;
- `corr(x, y)` — коэффициент корреляции между значениями параметра `x` и фактическим спросом `y`.

Если корреляция не может быть рассчитана из-за малой выборки или нулевой дисперсии параметра, важность принимается равной нулю.

Рекомендуемый вес рассчитывается нормировкой важностей:

```math
w_x^{rec} = \frac{s_x}{\sum_j s_j}
```

Плавное обновление веса:

```math
w_x^{new} = w_x^{old} + \eta (w_x^{rec} - w_x^{old})
```

где `\eta` — скорость обновления весов.

Если сумма важностей равна нулю, текущие веса не обновляются.

## 8. Индивидуальные и глобальные параметры

### 8.1. Индивидуальные параметры ресторана

К индивидуальным параметрам ресторана относятся:

- веса блока нагрузки;
- веса блока исторической востребованности;
- веса итогового индекса спроса;
- нижняя и верхняя границы сервисного сбора;
- исторические коэффициенты календарных классов;
- востребованность дней недели, временных интервалов и столов.

Все индивидуальные значения должны храниться с привязкой к `restaurantId`.

### 8.2. Глобальные параметры системы

К глобальным параметрам системы относятся:

- минимальное количество исторических наблюдений для перехода от дефолтных значений к истории;
- скорость обновления весов;
- коэффициент крутизны сигмоидальной функции;
- центр сигмоидальной функции;
- системные минимальные и максимальные ограничения сервисного сбора;
- дефолтные значения для новых ресторанов.

Рекомендуемые стартовые значения:

| Параметр | Значение | Назначение |
|---|---:|---|
| `T_hist` | 90 дней | период анализа исторических данных |
| `N_min,weights` | 50 | минимум успешных бронирований для обновления весов |
| `N_full,weights` | 150 | порог, после которого веса полностью исторические |
| `N_min,class` | 5 | минимум наблюдений для календарного класса |
| `N_full,class` | 20 | порог, после которого календарные коэффициенты полностью исторические |
| `N_min,table` | 50 | минимум бронирований с данными по столам |
| `N_full,table` | 150 | порог, после которого востребованность стола полностью историческая |
| `eta` | 0.1 | скорость плавного обновления весов |
| `k` | 8 | крутизна сигмоидальной функции |
| `c` | 0.5 | центр сигмоидальной функции |

## 9. Условия перехода от дефолтных значений к историческим данным

Исторические данные не используются сразу после добавления ресторана. Для нового ресторана применяются стартовые экспертные значения параметров и весов.

Для обновления весов должно выполняться условие:

```math
N_r^{success} \geq N_{min,weights}
```

Для календарных классов:

```math
O_{r,c} \geq N_{min,class}
```

Для параметра востребованности стола:

```math
N_r^{table} \geq N_{min,table}
```

Итоговое правило выбора значения:

```math
\theta_r =
\begin{cases}
\theta_0, & N_r < N_{min}, \\
(1 - \lambda_r)\theta_0 + \lambda_r\theta_r^{hist}, & N_{min} \leq N_r < N_{full}, \\
\theta_r^{hist}, & N_r \geq N_{full}.
\end{cases}
```

```math
\lambda_r = \frac{N_r - N_{min}}{N_{full} - N_{min}}
```

`\lambda_r` ограничивается диапазоном `[0; 1]`. Если `N_full = N_min`, переход считается мгновенным: до `N_min` используется `\theta_0`, с `N_min` — `\theta_r^{hist}`.

где:

- `\theta_r` — используемое значение параметра или веса ресторана `r`;
- `\theta_0` — стартовое экспертное значение;
- `\theta_r^{hist}` — значение, рассчитанное по истории ресторана `r`.

## 10. Пошаговый план реализации в коде

### Шаг 1. Создать пакет `pricing`

Создать новый пакет внутри `booking-service`:


### Шаг 2. Добавить настройки в `application.yml`

Добавить раздел:

```yaml
pricing:
  offer-ttl-minutes: 10
  sigmoid:
    k: 8
    center: 0.5
  history:
    period-days: 90
    min-bookings-for-history: 50
  system-limits:
    min-pricing-charge: 0
    max-pricing-charge: 10000
  defaults:
    calendar-context: 0.5
    table-demand: 0.5
    weights:
      load-block: 0.4
      historical-demand-block: 0.4
      calendar-context-block: 0.2
      occupancy: 0.45
      urgency: 0.35
      occupancy-urgency-interaction: 0.20
      weekday-demand: 0.35
      time-interval-demand: 0.45
      table-demand: 0.20
```

Создать класс `PricingProperties`, который будет читать эти значения через `@ConfigurationProperties(prefix = "pricing")`.

### Шаг 3. Создать DTO для API

Создать классы:

```text
PricingOfferRequest
PricingPreorderItemRequest
PricingOfferResponse
```

`PricingOfferRequest` должен содержать:

```text
restaurantId;
tableId;
visitStart;
visitEnd;
preorderItems.
```

`PricingPreorderItemRequest` должен содержать:

```text
dishId;
quantity.
```

`PricingOfferResponse` должен содержать:

```text
offerId;
restaurantId;
tableId;
preorderAmount;
pricingCharge;
totalAmount;
expiresAt;
calculatedAt.
```

### Шаг 4. Создать контроллер `PricingController`

Контроллер должен иметь метод:

```text
POST /api/pricing/offers
```

Задача контроллера:

```text
1. принять запрос;
2. получить идентификатор пользователя из JWT или SecurityContext;
3. вызвать PricingService;
4. вернуть PricingOfferResponse.
```

Контроллер не должен содержать математическую логику.

### Шаг 5. Создать основной сервис `PricingService`

`PricingService` должен управлять общим сценарием:

```text
1. проверить входные данные;
2. сформировать PricingContext;
3. передать контекст в PricingOfferService;
4. вернуть ответ для фронтенда.
```

Этот сервис не должен самостоятельно считать параметры модели.

### Шаг 6. Создать валидацию запроса

Создать `PricingValidationService`.

Проверки:

```text
restaurantId не null;
tableId не null;
visitStart не null;
visitEnd не null;
visitEnd позже visitStart;
visitStart позже текущего времени;
quantity > 0;
preorderAmount не отрицательный;
границы сервисного сбора корректны.
```

При ошибках выбрасывать `PricingValidationException`.

### Шаг 7. Создать `PricingContext`

`PricingContext` — главный объект, который передается во все параметры, блоки и расчетчик.

Он должен содержать:

```text
userId;
restaurantId;
tableId;
visitStart;
visitEnd;
requestTime;
preorderItems;
preorderAmount;
cartHash;
totalTablesCount;
occupiedTablesCount;
minPricingCharge;
maxPricingCharge;
pricingSettings.
```

### Шаг 8. Создать `PricingContextFactory`

`PricingContextFactory` должен собирать все данные для расчета:

```text
1. получить данные ресторана и стола;
2. получить количество занятых столов на выбранный интервал;
3. рассчитать сумму предзаказа по блюдам;
4. сформировать cartHash;
5. получить настройки ресторана;
6. вернуть PricingContext.
```

Для внешних данных использовать адаптеры/клиенты, а не обращаться напрямую к таблицам другого микросервиса.

### Шаг 9. Реализовать ценовое предложение `PricingOffer`

Создать:

```text
PricingOfferService
PricingOfferHashService
PricingOfferExpirationService
PricingOfferFactory
PricingOfferEntity
PricingOfferRepository
```

`PricingOfferService` должен:

```text
1. искать актуальное ценовое предложение по userId, restaurantId, tableId, visitStart, visitEnd и cartHash;
2. проверять срок действия предложения;
3. если предложение актуально — возвращать его;
4. если предложение отсутствует или устарело — вызывать PricingCalculator;
5. сохранять новое предложение;
6. возвращать результат.
```

TTL предложения — 10 минут.

`PricingOfferHashService` должен формировать стабильный hash корзины. Перед хэшированием позиции предзаказа нужно сортировать по `dishId`.

### Шаг 10. Создать сущности и миграции базы данных

Минимально нужны таблицы:

```text
pricing_offer
restaurant_pricing_settings
pricing_weight
pricing_calendar_coefficient
pricing_history_snapshot
```

`pricing_offer` хранит рассчитанные ценовые предложения.

`restaurant_pricing_settings` хранит границы сервисного сбора и включение динамического расчета.

`pricing_weight` хранит индивидуальные веса ресторана.

`pricing_calendar_coefficient` хранит коэффициенты календарных классов.

`pricing_history_snapshot` хранит агрегированные исторические наблюдения для обновления весов.

### Шаг 11. Реализовать параметры модели

Создать общий интерфейс:

```java
public interface PricingParameter {
    ParameterCalculationResult calculate(PricingContext context);
}
```

Реализовать параметры:

```text
OccupancyParameter
UrgencyParameter
WeekdayDemandParameter
TimeIntervalDemandParameter
TableDemandParameter
CalendarStatusParameter
```

Важно:

```text
OccupancyParameter использует формулу L_r = B_r / M_r.
UrgencyParameter использует экспоненциальную формулу.
WeekdayDemandParameter использует историю или дефолт.
TimeIntervalDemandParameter использует историю или дефолт.
TableDemandParameter использует историю или дефолт.
CalendarStatusParameter использует степени принадлежности и календарные коэффициенты.
```

Все значения должны быть ограничены диапазоном `[0; 1]`.

### Шаг 12. Реализовать блоки модели

Создать общий интерфейс:

```java
public interface PricingBlock {
    BlockCalculationResult calculate(PricingContext context);
}
```

Реализовать:

```text
LoadBlock
HistoricalDemandBlock
CalendarContextBlock
```

`LoadBlock` должен рассчитывать:

```math
B_{L,r} = w_L L_r + w_U U_r + w_{LU} L_r U_r
```

`HistoricalDemandBlock` должен рассчитывать:

```math
B_{H,r} = w_D D_r(d) + w_V V_r(t) + w_Q Q_r(q)
```

`CalendarContextBlock` должен рассчитывать:

```math
B_{C,r} = C_r
```

### Шаг 13. Реализовать работу с весами

Создать:

```text
PricingWeightService
PricingWeightProvider
PricingWeightNormalizer
PricingWeightCalculationService
PricingWeightUpdater
```

На первом этапе `PricingWeightProvider` может брать веса из `application.yml`.

На втором этапе он должен проверять наличие индивидуальных весов ресторана в таблице `pricing_weight`.

Правило:

```text
если истории недостаточно — использовать дефолтные веса;
если история накоплена — использовать индивидуальные веса ресторана;
если индивидуальных весов нет — использовать дефолтные веса.
```

### Шаг 14. Реализовать `PricingCalculator`

`PricingCalculator` должен выполнять полный расчет:

```text
1. вызвать LoadBlock;
2. вызвать HistoricalDemandBlock;
3. вызвать CalendarContextBlock;
4. рассчитать итоговый индекс спроса Z_r;
5. рассчитать P_r^{calc} через сигмоидальную функцию;
6. если preorderAmount = 0, установить pricingCharge = 0;
7. если preorderAmount > 0, использовать рассчитанный pricingCharge;
8. рассчитать totalAmount = preorderAmount + pricingCharge;
9. вернуть PricingCalculationResult.
```

```text
PricingMathUtils
NormalizationUtils
```

`PricingMathUtils`:

`NormalizationUtils`:

### Шаг 16. Реализовать исторический сервис

Создать `PricingHistoryService`.

Он должен получать из истории бронирований:

```text
количество успешных бронирований ресторана;
количество успешных бронирований по дням недели;
количество успешных бронирований по временным интервалам;
количество успешных бронирований по столам;
количество наблюдений по календарным классам;
количество доступных столов в наблюдениях.
```

Успешным считать бронирование, которое подтверждено рестораном и не отменено до наступления времени визита.

### Шаг 17. Реализовать обновление весов

Создать `PricingWeightCalculationService`.

Он должен:

```text
1. получить исторические наблюдения ресторана;
2. для каждого параметра или блока собрать ряд значений x;
3. собрать ряд фактического спроса y;
4. рассчитать corr(x, y);
5. взять только положительную часть корреляции;
6. нормировать важности;
7. получить рекомендуемые веса.
```

Создать `PricingWeightUpdater`.

Он должен применять формулу:

```math
w_x^{new} = w_x^{old} + \eta (w_x^{rec} - w_x^{old})
```

Если сумма важностей равна нулю, веса не обновлять.

### Шаг 18. Реализовать scheduler

Создать `PricingWeightsUpdateScheduler`.

Он должен запускаться по расписанию и выполнять:

```text
1. найти рестораны с достаточной историей;
2. сформировать исторические наблюдения;
3. рассчитать рекомендуемые веса;
4. плавно обновить веса;
5. сохранить веса в pricing_weight;
6. записать лог результата.
```

Позже можно добавить `PricingHistorySnapshotScheduler`, который будет заранее формировать агрегированные наблюдения.

### Шаг 19. Реализовать календарный справочник

Нужно определить источник данных для:

```text
рабочих дней;
выходных дней;
праздничных дней;
пиковых праздничных дней.
```

На первом этапе можно использовать простую реализацию:

```text
суббота и воскресенье — выходные;
список праздников хранится в application.yml или таблице;
пиковые праздники задаются отдельным списком.
```

Позже можно вынести это в отдельную таблицу или административный справочник.

### Шаг 20. Подключить расчет к созданию бронирования

При создании бронирования нужно:

```text
1. получить offerId от фронтенда;
2. найти PricingOfferEntity;
3. проверить, что предложение активно и не истекло;
4. проверить совпадение userId, restaurantId, tableId, visitStart, visitEnd и cartHash;
5. использовать pricingCharge из предложения;
6. сохранить pricingCharge и totalAmount в бронировании;
7. отметить предложение как USED.
```

Если предложение истекло, нужно вернуть ошибку и попросить фронтенд запросить новый расчет.

### Шаг 21. Обновить frontend

На стороне frontend нужно:

```text
1. при выборе ресторана, стола, времени и блюд вызывать POST /api/pricing/offers;
2. отображать preorderAmount, pricingCharge и totalAmount;
3. хранить offerId до создания бронирования;
4. при изменении корзины запрашивать новое ценовое предложение;
5. если истекло 10 минут, запрашивать новый расчет;
6. передавать offerId при создании бронирования.
```

### Шаг 22. Добавить тесты

Минимальные тесты:

```text
без предзаказа pricingCharge = 0;
с предзаказом pricingCharge > 0;
preorderAmount не влияет на размер pricingCharge;
totalAmount = preorderAmount + pricingCharge;
при одинаковой корзине hash одинаковый;
при изменении корзины hash меняется;
просроченное предложение не используется;
значения параметров остаются в диапазоне [0; 1];
сигмоида возвращает значение в пределах minPricingCharge и maxPricingCharge;
при недостатке истории используются дефолтные значения;
при достаточной истории используются исторические значения.
```

## 11. Минимальный порядок реализации

Если писать код самостоятельно, лучше реализовывать не всю структуру сразу, а по этапам.

На этом этапе исторические параметры можно временно возвращать из дефолтных значений.

## 12. Контроль соответствия модели

При реализации нужно проверить следующие пункты:

- сервисный сбор равен нулю, если предзаказ отсутствует;
- сумма предзаказа не влияет на размер сервисного сбора;
- итоговая стоимость равна сумме предзаказа и сервисного сбора;
- текущая загрузка считается как доля занятых столов;
- срочность рассчитывается экспоненциально;
- исторические параметры используют успешные бронирования;
- календарный параметр учитывает рабочие, выходные, праздничные и пиковые праздничные дни;
- блок нагрузки содержит совместное влияние загрузки и срочности;
- итоговый индекс спроса объединяет три блока;
- сервисный сбор рассчитывается сигмоидальной функцией;
- значения не выходят за границы ресторана;
- веса ресторана индивидуальны;
- исторические данные используются только после накопления достаточной статистики;
- обновление весов выполняется плавно;
- устаревшее ценовое предложение нельзя использовать при создании бронирования.
